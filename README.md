## 平特肖与特码风险控制（测试分支）

- 正常开奖按顺序读取：前 6 个号码为平码，第 7 个号码为特码；若输入超过 7 个号码，使用前 6 个平码和第 7 个特码，并提示忽略多余号码。
- 平特肖、平特尾及连肖类玩法只使用前 6 个平码号码对应的生肖/尾数。第 7 个特码生肖或尾数不会单独触发这些玩法；如果相同生肖/尾数也出现在前 6 个平码中，仍按平码命中。
- 风险页分开展示平特肖与特码风险，沿用现有下注记录、赔率和回水设置；同时显示最大预计赔付及净盈亏（赔付 + 回水 − 该类下注额，正数代表庄家潜在亏损）。
- 平特肖最坏情景按前 6 个平码最多出现 6 个不同生肖估算；若相关赔率未填写，会显示“待填赔率”，不把未知风险误报为 0。
- 该修改目前只用于 `feat/private-cloud-learning-sync` 测试分支，未合并到 `main`。

## 平特0尾与五不中结算（测试分支）

- 赔率设置新增“平特0尾”独立赔率：默认 2.1 倍带本；其余 1–9 尾使用“平特尾”赔率，默认 1.85 倍带本。按通知口径，平特尾只看前六个平码的尾数，第七个特码的尾数不单独触发。
- “带本”按总赔付 = 命中下注额 × 赔率计算；净盈亏 = 总赔付 + 回水 − 本笔总下注额。
- 五不中（当前也由同一赔率设置供六不中、七不中使用）以全部七个开奖号码判断。只要任一所选号码出现在前六个平码或第七个特码中，即为未中；所选号码均未开出时按“不中赔率”计算赔付。
- 通知中没有给出五不中赔率，因此设置里的“五/六/七不中（共用赔率）”默认留空。必须填入你实际使用的赔率后才会计算命中赔付；不会把未知赔率当作 0 或默认猜测。
- 当前修改只在 `feat/private-cloud-learning-sync` 测试分支，未合并到正式 `main`。

## 本地解析器补充：每个 N 与玩法前置（测试分支）

- `每个 / 每位 / 每只 + 金额` 一律按“各”处理：`17 29 41 每个3块`、`17 29 41每位3`、`每位 十 块` 都会解析成 3 个号码各 3 / 10。
- 五不中、六不中、七不中支持玩法写在号码前面，金额可以在末尾用空格、逗号、点号、`各`、`=` 或单位分隔：
  `五不中 04 06 05 11 12 200`、`五不中 0406051112 200`、`五不中 04.06.05.11.12 200`、
  `五不中 04 06 05 11 12=200`、`五不中:04,06,05,11,12 200块` 都能识别为 200 元一注。
- 号码数量必须与玩法一致（五不中 5 个、六不中 6 个、七不中 7 个）。对不上时整条不解析并给出提示，
  不会再降级成“特码总单 × 每个号码”而把 200 算成 1000。
- 顺带支持 `波色 红 100` / `波色红100` 这种带玩法标签的写法。
- 直接粘贴整段微信/群聊记录也可以：会自动去掉「昵称 + 2026年11月02日 18:57」这类头和只有“1”的应答，并在消息之间断开，避免把时间里的 `2026`、`57` 当号码，或把两条消息的号码行合并成一笔。

## AI 长文本与 Token 限额恢复

- 检测 Groq 413 / rate_limit_exceeded 且明确属于 TPM（每分钟 Token）限额的错误。
- 首次超限后先移除历史示例并使用较短提示词重试，以减少重复提示词开销。
- 仍超限时按原文顺序分段解析；多行玩法标题可作为分段上下文提示，分段结果最后按顺序合并。
- 如果仍处于限额窗口，会在界面提示等待并重试；特别长的内容仍可能需要等待或由用户按玩法区块拆分。
- 分段结果会提示用户重点核对边界处的玩法、号码和金额；AI 不保证每种输入都能自动正确识别。添加记录前仍需人工核对。

## AI 结果自检与自动修正

- AI 返回结果后，先用确定性规则和原文对账：每个 `items[].raw` 必须能在原文里逐字找到；原文里的数字必须被某个条目承接（防漏笔）；`raw` 里大于 49 的数字必须等于该项 `amount`（防金额读错）；原文提到的玩法必须出现在结果的玩法字段里（防改玩法）。
- 自检发现 high 级别问题时，会把“原文 + 上一次 JSON + 问题清单”作为修正请求再发一次（只重试一次，避免额度翻倍）；修正后问题变少才采用新结果，否则保留第一次结果并继续提示核对。
- 仍有问题时，预览里会以「AI 自检：…」逐条列出，并把结果标记为“请核对”，添加记录前仍需人工确认。
- 自检逻辑独立在 `ai-guard.js`，可在 Node 下直接跑测试，不依赖浏览器。

## 主要文件

- index.html：响应式 UI、输入页、解析预览卡片、汇总/风险/设置页面。
- app.js：界面状态、AI 调用、Groq 错误恢复、预览展示与统计交互。
- ai-guard.js：AI 结果与原文的确定性对账、修正提示词生成。
- learning.js：本地学习案例、人工纠错、相似检索、导入导出、私人云端同步。
- core.py：解析与统计内核。
- main.py / buildozer.spec：Kivy 移动应用与 Android 打包。
- tests/：解析、学习库与 AI 长文本回归测试。
- worker/：可选 Cloudflare Worker + D1 私人学习库同步接口。

## 基本测试

    python -m py_compile core.py
    node --check app.js
    node --check learning.js
    node --check ai-guard.js
    node tests/test_learning_logic.js
    node tests/test_ai_resilience.js
    node tests/test_ai_guard.js
    python -m unittest discover -s tests -v

Worker 的本地测试与部署说明见 worker/README.md。云同步密钥只应配置在 Cloudflare Worker Secret 和你本人设备的浏览器中；不要把同步令牌或 Groq API Key 提交到代码仓库。

## 数据与发布安全

- 当前优化已合入 `feat/private-cloud-learning-sync` 测试分支，尚未合并到生产 `main`。Worker 的允许来源配置已更新到仓库；要让正在运行的 Worker 生效，仍需从 `worker/` 目录重新部署。
- 首次同步或进行大规模导入前，请导出学习库 JSON 备份。
- 云同步范围为学习案例、待处理样本、删除标记和学习计数；不包括下注记录、赔率、开奖号码或 Groq API Key。
- 修改过的解析和 AI 恢复逻辑应在测试网站进行实测；新增测试通过并不等于覆盖了所有下注格式。
